# 并发写隔离

**状态**：草案。隔离原语与授权收窄的先例来自 `references/designs/multi-root-workspace/`（已收敛的设计），并发调度部分尚未经过实践验证。

**适用形态**：并行 fan-out、竞争择优；委派与流水线仅在 worker/阶段会写且可能并行时适用。

**解决的问题**：多个 worker 同时动文件时，谁能写哪里、冲突怎么办、失败怎么回收。

---

## 1. 底座是 worktree，不是目录约定

FylloCode 已有 linked worktree（`<folderPath>/.worktrees/<changeId>`），这是现成的隔离原语：每个 worker 一个 worktree，物理隔离，失败直接丢弃。

**不要用「约定每个 worker 只改自己那部分文件」来替代物理隔离。** 约定靠 agent 自觉遵守，而 agent 不可靠；worktree 是文件系统层面的边界。

## 2. 三条可直接迁移的先例

multi-root 评审已经把同构问题推过一遍，不需要重新设计：

| multi-root 结论                                                                | 在并发写隔离中的对应                                                  |
| ------------------------------------------------------------------------------ | --------------------------------------------------------------------- |
| **I18** apply/archive 的文件系统 scope 与 MCP descriptor 同步收窄为 owner-only | worker 的可写目录与其工具授权必须**同步**收窄，不能只收窄一边         |
| **I19** run 创建时固定 `folderId + worktreePath`，执行期不重新解析             | worker 派发时固定工作目录，运行期不按当前状态重算                     |
| **I29** 成员移除后，既有 session 的授权必须撤销，不因全局仍存在而恢复          | 编排状态变更（worker 被取消、目标被移除）时必须撤销存活 worker 的授权 |

I18 那条尤其容易漏：只把 worker 的 `cwd` 限制住，却仍给它一份覆盖全仓的工具授权，等于没隔离。

## 3. 派发时必须固定的东西

| 项           | 说明                                                  |
| ------------ | ----------------------------------------------------- |
| **工作目录** | 具体的 worktree 路径，派发时确定，运行期不重算（I19） |
| **可写范围** | 该 worktree 之内；越界写入应被拒绝而非警告            |
| **可读范围** | 可以宽于可写范围，但必须显式列出                      |
| **工具授权** | 与可写范围同步收窄（I18）                             |

## 4. 冲突与合并

v1 建议**不做自动合并**：

- **fan-out**：任务切分时就应保证 worker 之间不重叠。重叠说明切分错了，应该重新切，而不是靠合并兜底。
- **竞争择优**：本来就只采纳一个，其余 worktree 直接丢弃，不存在合并问题。

真正需要合并多个 worker 产出的场景，应视为独立设计课题——multi-root 评审在 §11 明确把「跨仓库原子提交」划出 v1 边界，理由同样适用于此：分布式提交与失败恢复的复杂度，不应通过放宽隔离来绕过。

## 5. 回收

| 情形          | 处理                                                         |
| ------------- | ------------------------------------------------------------ |
| worker 成功   | 产出按 `handoff-artifact.md` 返回；worktree 按流程合并或保留 |
| worker 失败   | worktree 直接丢弃，**连同其上下文一起丢弃**                  |
| worker 被取消 | 先撤销授权再回收目录，不得先删目录后关进程（I29 的次序要求） |
| 编排整体中止  | 逐个撤销 + 回收；不得留下半清理状态                          |

「失败即丢弃」是竞争择优形态的核心收益：主会话不会被一次跑偏的探索污染。

## 6. 待定

- **worktree 的分配与回收由谁负责**：编排器、还是各 worker 自助。倾向编排器——self-service 会重现 multi-root I8 的 registry 并发问题。
- **并发上限**：受 Agent 进程数与磁盘占用约束，尚无依据给建议值。
- **非 Git 目录的隔离**：worktree 只适用于 Git 仓库；multi-root 已明确成员可以是 non-Git Folder，这类目标的隔离手段未定。
- **只读 worker 是否也需要隔离**：倾向不需要，但需确认工具授权不会因共享而互相影响。
