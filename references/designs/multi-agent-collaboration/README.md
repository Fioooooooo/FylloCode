# Multi-agent Collaboration

本目录收录 FylloCode 中**多个 Agent 协同完成一项工作**的协作设计。

与单 Agent 会话不同，多 Agent 协作要额外解决三类问题：

1. **终止** —— 两个 Agent 之间没有天然的停止条件，需要外部强制；
2. **状态交换** —— Agent 之间靠共享文件（mailbox）通信，格式不当会在上下文压力下丢内容；
3. **权限与冲突** —— 谁能改什么、谁在什么时候发言。

## 协作形态分类

| 分类             | 一句话                                         | 适用                                                       | 注意                                                           |
| ---------------- | ---------------------------------------------- | ---------------------------------------------------------- | -------------------------------------------------------------- |
| **委派**         | 主 agent 把子任务外包给 worker，只收结果       | 子任务读得多、返回得少（搜索、清点、跑测试诊断）           | 验收标准必须派发时写死，别让被委派方定义什么叫做完             |
| **并行 fan-out** | 同类任务同时派给多个 worker，各做各的互不通信  | 任务天然可切分且互不重叠（多仓库同类改动、多来源调研）     | 结果要区分「合法空 / 目标缺失 / 执行失败」三态，别把失败混成空 |
| **竞争择优**     | 同一任务派给多个 worker 用不同思路做，再挑一个 | 方案不确定，且试错成本低于纠错成本                         | 评分标准要前置，否则裁判会为已产出的结果找理由                 |
| **流水线**       | 按阶段串行交接，每阶段换一个角色和权限         | 阶段边界清晰的既定流程（如 propose → implement → archive） | 阶段之间交接结构化产物，散文交接一定会丢信息                   |
| **接力**         | 同一任务上下文快满了，换个新 agent 接着做      | 长任务、上下文压力大                                       | 交接状态必须可序列化，写不出来的隐性理解一定会丢               |
| **验证/对抗**    | 一方产出，一方设法证伪                         | 正确性可执行验证的场合（测试、安全、性能）                 | 这是唯一自带终止条件的形态，能改造成它就别用评审               |
| **评审往返**     | 双方就同一产物多轮讨论直到收敛                 | 产出无法自动验证、只能靠判断的东西（设计、规范）           | 没有内生终止条件，必须靠外部强制停止                           |

**前六种的终止条件都是内生的，只有评审往返需要外部强制**——这也是它最先暴露问题、并率先形成契约的原因。

## 为什么不给每种形态各写一份文档

因为它们之间的差异，大部分只是**两个填空**。

如果真给 fan-out、委派、流水线各建一个平级目录，每份文档会有 80% 是重复的——角色定义、证据要求、发言规范、编号规则，全一样。真正不同的只有终止条件与验收标准两处：

| 形态         | 终止条件                     | 验收标准                   |
| ------------ | ---------------------------- | -------------------------- |
| 委派         | 验收标准满足                 | 派发时写死的可判定条件     |
| 并行 fan-out | 全部 worker 返回（含失败态） | 每个 worker 的三态结果齐全 |
| 竞争择优     | 评分完成                     | 前置的评分 rubric          |
| 流水线       | 阶段产物通过校验             | 产物 schema                |
| 接力         | 原任务完成                   | 状态序列化完整             |
| 验证/对抗    | 测试通过或给出失败用例       | 可执行测试                 |
| 评审往返     | 严重度闸门 + 递减触发器      | 议题全部收敛或显式挂起     |

**每一行都填在同样的两个格子里。** 而 `agent-review/templates/contract.md` 里已经有「终止条件」这一节。所以发起一次 fan-out 协作时不需要读一份新文档，只需要新建一个 `contract.md`，把这两格填成 fan-out 的值。

但有两样东西不是填空，是**得真造出来的机制**，因此各自成文：

- **交接产物的形态** —— 委派、流水线、接力都是「A 的输出就是 B 的输入」。这需要定义一套结构（带哪些字段、怎么序列化、接收方怎么校验完整），不统一规定就会各自发明，且大概率都退化成散文。
- **并发写隔离** —— fan-out 与竞争择优会有多个 worker 同时动文件。这是运行时机制（worktree 分配、冲突检测、失败回收），不是文档字段。

**评审往返之所以配得上独立目录**，是因为它的终止不是填个值就完事——严重度闸门、递减触发器、人类检查点，是一整套需要编排器执行的机制，比其他六种加起来都复杂。

**验证/对抗不需要独立目录**：终止条件内生（测试通过或给出失败用例），交接产物由 `handoff-artifact.md` 覆盖——而且它是那份规范的**最佳形态**，因为它的交接物是可执行的，不存在散文丢信息的问题。

## 文档结构与适用范围

```text
multi-agent-collaboration/
├── README.md              # 本文件：分类与拆分依据
├── handoff-artifact.md    # 交接产物形态（草案）
├── write-isolation.md     # 并发写隔离（草案）
└── agent-review/          # 评审往返协作契约
    ├── README.md
    └── templates/         # MAILBOX.md / contract.md / issue.md
```

| 形态         | `agent-review/` | `handoff-artifact.md`  | `write-isolation.md` |
| ------------ | --------------- | ---------------------- | -------------------- |
| 委派         | —               | ✅                     | 仅当 worker 会写     |
| 并行 fan-out | —               | ✅（返回侧三态）       | ✅                   |
| 竞争择优     | —               | ✅                     | ✅                   |
| 流水线       | —               | ✅                     | 仅当阶段并行         |
| 接力         | —               | ✅                     | —                    |
| 验证/对抗    | —               | ✅（最佳形态：可执行） | —                    |
| 评审往返     | ✅              | ✅（mailbox 是其特例） | —                    |

任何形态都还需要一份自己的 `contract.md`，模板见 `agent-review/templates/contract.md`。

## 与实现的关系

本目录的文档描述**协作契约**，不描述编排层实现。契约中标注为「编排器强制」的条款需要由承载多 Agent 的运行时保证；标注为「Prompt 约定」的条款写入各方的系统提示。

编排层实现（主 Agent 拉起 ACP subagent）会独立演进，届时应回查本目录确认契约条款是否仍被满足，而不是反过来让契约迁就实现。
