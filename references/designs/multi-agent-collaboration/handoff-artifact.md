# 交接产物形态

**状态**：草案。核心原则来自 `agent-review/` 的实测，具体字段设计尚未经过实践验证。

**适用形态**：委派、流水线、接力、验证/对抗、评审往返（mailbox 是本规范的一个特例）。

**解决的问题**：这些形态都是「A 的输出就是 B 的输入」。如果不统一规定交接物的形态，每种协作会各自发明，且大概率都退化成散文——而散文交接会丢信息。

---

## 1. 核心原则：越接近可执行，越不丢信息

交接物按可靠性排序：

| 形态             | 例子                          | 接收方能否自动判断是否满足 |
| ---------------- | ----------------------------- | -------------------------- |
| **可执行**       | 一个失败的测试用例            | 能，跑一遍即可             |
| **结构化**       | `{folderId, path, line}` 记录 | 能，schema 校验            |
| **带证据的断言** | 「X 有问题，见 `a.ts:12`」    | 部分，要人/agent 判断      |
| **散文**         | 「这里的错误处理有点问题」    | 不能                       |

**能往上走一级就往上走一级。** 验证/对抗形态之所以是最佳形态，正是因为它的交接物天然落在第一档——失败用例既是问题描述，也是验收标准，还是回归测试。

`agent-review/` 里投入产出比最高的规则（事实性断言必须附 `文件:行号`）本质上就是把交接物从第四档强行拉到第三档。实测中它抓出了 reviewer 的 6 处错误推导。

## 2. 派发侧必须携带

无论哪种形态，A 交给 B 的东西至少要有：

| 字段           | 说明                                                   | 缺失后果                       |
| -------------- | ------------------------------------------------------ | ------------------------------ |
| **任务**       | 一句话，可判定的动词                                   | B 自行发挥                     |
| **验收标准**   | **可判定**的完成条件，派发时写死                       | B 定义什么叫做完，A 无依据验收 |
| **作用域**     | 可读/可写的目录、可用工具、禁止触碰的范围              | B 越界，或不敢动该动的东西     |
| **上下文指针** | 文件路径、议题编号、既有结论的位置——**指针，不是内容** | 内容出现两份副本，副本会漂移   |
| **返回格式**   | 期望 B 返回什么形态（见 §3）                           | B 返回散文，A 无法自动处理     |

> **验收标准由派发方定义，不由接收方定义。** 这是委派形态最容易塌的一条，和评审形态里「Agent 不得代产品方作答」是同一类问题。

**上下文只给指针不给内容**：`agent-review/` 实测中，人类手工转发时大量复述 mailbox 内容，产生了同一份内容的两个副本。自动化流程里这既浪费又制造漂移风险。

## 3. 返回侧必须携带

### 3.1 三态结果

返回状态**至少**要能区分：

- `ok` —— 完成，附结果；
- `empty` —— 合法地没有内容（查了，确实没有）；
- `missing` —— 目标不存在；
- `failed` —— 执行失败，附原因。

**`empty` 与 `failed` 不可混同。** 这是 multi-root 评审 I22 的结论（aggregate reader 三态），在 fan-out 形态里是同一个问题：N 个 worker 里有一个失败，如果它返回空结果，汇总方会当作「那边确实没有」。

fan-out 的汇总产物必须逐 worker 标注状态，并标明整体完整性（全部成功 / 部分失败）。

### 3.2 证据

结果中的事实性断言按 §1 的原则附证据。已在共享事实表中的用编号引用，不重复验证。

### 3.3 未尽事项

B 未完成或主动缩减的部分必须显式列出，不能静默省略。静默省略会让 A 以为任务已完整覆盖。

## 4. 接力形态的特殊要求

接力（同一任务换新 agent）的交接物是**状态快照**，比其他形态更难：

- 必须包含：已完成的步骤、当前结论、未决问题、下一步；
- 必须包含：已排除的方案**及排除理由**——否则接手方会重走死路；
- **诚实前提**：写不出来的隐性理解一定会丢。

最后一条是硬限制，不是可以靠格式解决的问题。判断标准：**这个任务能不能写成一份自包含的描述？** 写不出来，说明它依赖的隐性上下文太多，不适合交接——该继续做完，或者换个切分方式。

## 5. mailbox 是本规范的一个特例

`agent-review/` 的 mailbox 格式是「双向、多轮、长期存续」条件下的交接产物实现：

| 本规范的要求 | mailbox 中的对应物                       |
| ------------ | ---------------------------------------- |
| 任务         | `MAILBOX.md` 的「本轮任务」              |
| 验收标准     | `contract.md` 的终止条件                 |
| 作用域       | `contract.md` 的范围与产物权限           |
| 上下文指针   | `MAILBOX.md` 的读取顺序 + `open/<ID>.md` |
| 返回格式     | `open/<ID>.md` 的往返记录骨架            |
| 证据         | 事实表 `F<n>` + `文件:行号`              |
| 三态         | 议题级别 + 待办方                        |

单向、一次性的形态（委派、fan-out）不需要这么重——它们的交接物可以是一次消息传递，不必落盘成多文件。**落盘的必要性来自「多轮」和「需要事后追溯」，不是来自「多 agent」。**

## 6. 待定

- 交接物是消息还是文件，由编排层决定；本规范只约束**内容**，不约束载体。
- 是否需要机器可校验的 schema（JSON Schema / zod）。`agent-review/` 的经验说明**人工维护的一致性一定会漂移**（实测 4 处），所以倾向于要。
- 跨形态的字段命名统一。
