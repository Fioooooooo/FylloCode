# Agent-Review 协作契约

**适用场景**：一方产出（author）、一方评审（reviewer）的多轮往返协作。典型用例是设计方案评审、代码评审、规范审查。

**状态**：草案。来自一次真实的 28 轮双 Agent 评审实验，每条规则都对应该实验中的一次实测失败或一次验证有效的做法。

---

## 0. 实验来源

本契约的经验基础是 `references/designs/multi-root-workspace/` 的评审：Claude 任 reviewer、Codex 任 author，人类（Fio）在中间手工转发消息，历时 28 轮、36 个议题（12 个阻塞级）。

关键观测：

| 观测                                                                                                            | 导出的条款  |
| --------------------------------------------------------------------------------------------------------------- | ----------- |
| 协作规则有 9 条，但**没有一条能让循环自己停下来**；规则里显式写着「交由人类裁决」                               | §2 全部     |
| **最后 8 轮（R21–R28）产出的阻塞级议题为 0**，约 30% 的轮次花在非阻塞尾巴上                                     | §2.1 / §2.2 |
| 修复本身在制造新表面：I33（tombstone）→ I35（清理边界）→ I36（provenance 唯一性），三层，每层由上一层的修复引入 | §2.3 / §3.4 |
| author 接受率约 92%（36 项中仅 3 处拒绝），双方之间几乎没有摩擦                                                 | §3.5        |
| 两次最有价值的介入都来自人类，不来自任何一方 Agent                                                              | §2.4        |
| reviewer 有 6 处事实性错误推导，**全部由「断言必须附 `文件:行号`」这条规则抓出**                                | §3.1        |
| 单个 mailbox 文件累积到约 2000 行时，**双方开始丢内容**，被迫中途拆分                                           | §4 全部     |
| 拆分后仍出现 4 处跨文件引用过期（文件名、编号区间、复选框状态、章节编号重复）                                   | §5          |

> ⚠️ 这些数字来自**有人类在中间转发**的流程。人类转发本身是一个隐性的限速器和 sanity check；自动化之后该限速器消失，**自动版本需要的约束比手动版更多，不是更少**。

## 1. 角色与权限

| 角色             | 权限                                                          |
| ---------------- | ------------------------------------------------------------- |
| **author**       | 唯一可修改**被评审产物**的一方；在 mailbox 中回应、修订、反驳 |
| **reviewer**     | 对被评审产物**只读**；只在 mailbox 中提出、质疑、复核、反驳   |
| **human**        | 裁决产品决策与僵持；决定终止；不承担消息转发                  |
| **orchestrator** | 不参与内容；执行 §2 的终止机制、校验 §5 的不变量、控制发言权  |

**单向写权限是硬约束。** 双方同时可改同一产物会产生编辑冲突与「谁改的」归属问题；实验中该约束（原规则 8）从未被违反，也从未成为瓶颈。

reviewer 有一个例外的写权限：**收敛记账**（把结论同步进 `decisions.md`、把议题文件移入 `archive/`）。这是流程操作而非内容修改，由收敛当轮的复核方执行。

## 2. 终止机制（编排器强制）

> **本节条款不能只写进 prompt。** Agent 无法可靠地自我终止：在任何一轮，「我又发现了一个真问题」都比「这个不值得再来一轮」更符合其行为倾向。实验中 reviewer 明知 I36 是低级别、无用户可见损失、两行可修，仍然开了正式议题。

### 2.1 严重度闸门（最高杠杆）

**只有阻塞级议题可以触发新一轮往返。** 中/低级别一律写入「实施约束清单」，随产物交付给下游（spec、测试、实现任务），不重启循环。

- 定级由 reviewer 给出，author 可反驳定级本身（这也是一种合法分歧）。
- 清单必须是**产物的一部分**，不是 mailbox 的一部分——mailbox 会休眠，产物不会。

这条把无限长的尾巴变成有限清单，且不丢失任何发现。实验中若一开始就有此条，I30–I36 七项里至少五项不会各占一轮。

### 2.2 递减触发器

**连续 N 轮零阻塞发现（默认 N = 2）→ 编排器强制中止往返，产出「建议关闭」报告交人类。**

由编排器数数，不由 Agent 判断。实验中该触发器会在 R24 左右触发，大致就是应该停的位置。

### 2.3 修订预算与 delta 界定

每次修订**必须在 mailbox 中声明本次引入了什么**：

- 新增/变更的持久化字段与 schema；
- 新增的不变量；
- 新增的对用户的承诺（尤其是不可逆操作的措辞）。

**下一轮只审这个 delta，不重开全文。**

实验中 I33 → I35 → I36 那条链，如果有此条会变成「tombstone 引入了 `cleanupState` 与一条『永久删除不可恢复』的承诺」，评审者一次性针对这两项检查，而不是分三轮偶然撞见。

### 2.4 人类检查点

自动化不等于无人。至少三处强制升级：

1. **开始前** —— 确认范围与预算（写入 `contract.md`）；
2. **递减触发时** —— 确认关闭或授权继续；
3. **涉及产品决策时** —— Agent 不得代产品方作答。

第 3 点在实验中被 author 正确执行过一次（拒绝替产品方决定两项待确认事项），结果是人类的回答**推翻了双方已接受 20 多轮的一个前提**。这类价值无法由 Agent 之间的往返产生。

### 2.5 成本可见

每轮向人类展示累计轮次、累计 token/时长、最近若干轮的阻塞级产出。

实验中若一直可见「已 22 轮、最近 8 轮零阻塞」，停止决定会来得更早。

### 2.6 轮次预算

在 `contract.md` 中声明软预算（触发人类检查点）与硬预算（强制中止）。

**这是本节最弱的机制**，因为合理轮数与产物规模强相关——实验中一份 117 KB 的设计文档合理消耗约 20 轮。预算的作用是兜底，主力是 §2.1 与 §2.2。

## 3. 发言规范（Prompt 约定）

### 3.1 事实性断言必须附证据

格式为 `文件路径:行号`。未核实的推测必须显式标注为推测。

实验中 reviewer 的 6 处错误推导——包括一个完整但不成立的安全攻击序列——全部由此条抓出。**这是投入产出比最高的一条规则。**

### 3.2 共享事实表，不重复验证

已核实的事实进入编号事实表（`F1`、`F2`…），双方均可引用，不再重复 grep。实验中积累到 F45，显著减少了重复核实。

### 3.3 显式撤回协议

改变立场时**新增一条发言**并写明「撤回 / 收回 / 维持」，不修改己方或对方的历史发言。

这条让记录保持诚实。实验中 8 处撤回被完整保留，包括「哪一方在哪一轮错了」，这对后续判断双方可靠性有直接价值。

### 3.4 author 需要评估成本，拒绝是预期行为

**明确写入 author 的 prompt：接受不是默认，评估「改这个的收益是否抵得上成本」是职责的一部分。**

实验中 author 接受率约 92%，仅 3 处拒绝——但那 3 处质量都很高（拒绝代产品方作答、拒绝造出一个「已知不可运行但仍启动」的第三种状态、拒绝采用分页方案）。零摩擦的双方不会收敛。

### 3.5 允许分歧存续

`僵持` 是合法终态，交人类裁决。不为收敛而单方让步。

### 3.6 范围约束

`contract.md` 中声明本次评审的范围。**范围外的既有缺陷即使发现也另行记录，不在本次收敛。**

实验中此条被正确援引多次，是少数几个真正抑制了议题发散的条款。

### 3.7 唤醒消息只含指针

编排器唤醒对方时，消息体只包含：角色、mailbox 路径、本轮任务（议题编号）、必读文件清单。**不复述 mailbox 内容。**

复述会产生同一份内容的两个副本，而副本会漂移。实验中人类手工转发时大量复述，在自动化流程里是纯粹的浪费与风险。

## 4. Mailbox 格式

### 4.1 设计目标

1. **每轮必读集合有界**，且不随议题总数增长；
2. **单文件有硬上限**，杜绝「累积到丢内容」；
3. **每份内容只有一个副本**，杜绝跨文件漂移；
4. **归档是移动而非复制**，杜绝重复维护。

### 4.2 布局

```text
<review-name>/
├── MAILBOX.md          # 唯一入口：状态板 + 读取顺序。硬上限 150 行
├── contract.md         # 本次评审的契约实例。创建后基本不变
├── decisions.md        # 已收敛结论 + 事实表。按需查阅，非每轮必读
├── open/               # 未收敛议题，一个议题一个文件
│   ├── I34.md
│   └── I35.md
└── archive/            # 已收敛议题的完整往返，文件名不变
    ├── I33.md
    └── ...
```

### 4.3 每份文件的契约

| 文件              | 写入者           | 写入方式        | 上限   | 每轮必读         |
| ----------------- | ---------------- | --------------- | ------ | ---------------- |
| `MAILBOX.md`      | 发言方（每轮）   | **整节替换**    | 150 行 | ✅               |
| `contract.md`     | 人类（开始时）   | 基本不变        | 100 行 | ✅               |
| `open/<ID>.md`    | 双方             | **末尾追加**    | 300 行 | ✅（仅未收敛的） |
| `decisions.md`    | 收敛当轮的复核方 | 追加一节        | 无硬限 | ❌ 按索引查      |
| `archive/<ID>.md` | 无（只读）       | 由 `open/` 移入 | —      | ❌ 仅追溯时      |

**每轮必读集合 = `MAILBOX.md` + `contract.md` + 全部 `open/*.md`。** 未收敛议题通常 2–5 个，合计 800 行以内，且**不随已收敛议题数量增长**——这是相对原方案的核心改进。

### 4.4 `MAILBOX.md` 骨架

只放**不可推导的状态**，不放任何叙述：

```markdown
# <review-name> · Mailbox

**轮次**：R24 | **待办方**：author | **状态**：进行中
**被评审产物**：<path>

## 未收敛

| ID  | 一句话议题 | 级别 | 待办方 | 提出轮次 |
| --- | ---------- | ---- | ------ | -------- |
| I34 | ...        | 阻塞 | author | R24      |

## 已收敛

| ID  | 一句话议题 | 级别 | 收敛轮次 |
| --- | ---------- | ---- | -------- |
| I33 | ...        | 高   | R24      |

## 本轮任务

<一句话。指向 open/ 下的具体文件，不复述内容。>
```

**禁止**在 `MAILBOX.md` 中出现：逐轮叙事、「本轮净结果」、进度回顾、待办复选框清单。这些在实验中全部变成了过期内容——本次会话开始时发现的 4 处不一致里有 3 处出自这类段落。

### 4.5 `open/<ID>.md` 骨架

```markdown
# I34 · <标题>

**级别**：阻塞 | **提出**：R24 · reviewer | **待办方**：author

## 问题陈述

<不随轮次变化。附 文件:行号 证据。>

## 往返记录

**[R24] reviewer：** ...

**[R25] author：** ...
（修订声明：新增字段 X、新不变量 Y、新用户承诺 Z）

## 共识结论

_待复核。_
```

### 4.6 状态转移

| 事件       | 操作                                                                                    |
| ---------- | --------------------------------------------------------------------------------------- |
| 提出新议题 | 创建 `open/<ID>.md`；`MAILBOX.md` 未收敛表增行                                          |
| 往返       | 追加到 `open/<ID>.md` 的往返记录末尾；更新 `MAILBOX.md` 的待办方与轮次                  |
| **收敛**   | 结论写入 `decisions.md` → `git mv open/<ID>.md archive/<ID>.md` → `MAILBOX.md` 表间移行 |

归档是一次 `git mv`，**没有复制、没有重写、没有第二份副本**。原方案按轮次打包归档（`rounds-R18-R20.md`）需要人工搬运整段文本，且事后查找是按议题查的，轮次分组无人使用。

### 4.7 结论只有一个副本

`decisions.md` 存**结论**；`archive/<ID>.md` 存**往返辩论**（含已撤回的错误推导），末尾指向 `decisions.md` 的对应小节。

`archive/` 里必须有醒目警告：**不要从归档取结论**——里面混有已被证伪的论述。实验中该警告是必要的，归档中至少有 6 处错误推导。

### 4.8 编号规则

- 议题编号 `I<n>`、事实编号 `F<n>` 全局递增，**不复用**；
- `MAILBOX.md` 记录下一个可用编号；
- 编号一旦分配，文件名固定，跨文件引用永远有效。

## 5. 不变量（编排器可机器校验）

每轮交接前校验，不通过则拒绝交接。实验中这些漂移全部靠人工发现，共 4 处。

1. `MAILBOX.md` 未收敛表中的每个 ID ⟺ `open/` 下存在同名文件（双向）；
2. `archive/` 下每个 `<ID>.md` 在 `MAILBOX.md` 已收敛表中有一行，且在 `decisions.md` 中有对应小节；
3. 议题编号无重复、无跳号；`MAILBOX.md` 声明的下一个编号 = 最大编号 + 1；
4. 每个 `open/<ID>.md` 最后一条发言的发言方 ≠ `MAILBOX.md` 标注的待办方（发言后待办方必须易手）；
5. 所有文件行数不超过 §4.3 的上限；
6. 跨文件引用（文件名、编号区间如 `I1–I33`、`F1–F45`）与实际一致；
7. `MAILBOX.md` 的轮次 = 全部 `open/*.md` 中出现的最大轮次。

**交接原子性**：`MAILBOX.md` 必须在交接前更新完毕。否则下一方读到半更新的状态板——而状态板被声明为唯一真相来源。

## 6. 反模式

实验中实际出现过的，逐条对应上面的条款：

| 反模式                     | 后果                                         |
| -------------------------- | -------------------------------------------- |
| 单文件持续追加             | 约 2000 行时双方开始丢内容                   |
| 状态板信息在正文中重述     | 3 处叙述段落全部过期，与状态板矛盾           |
| 待办复选框清单与状态板并存 | 复选框长期停留在「待复核」，与已收敛状态不符 |
| 归档按轮次打包             | 查找按议题进行，轮次分组无人使用；搬运成本高 |
| 章节编号手工维护           | 出现两个 `## 4.`                             |
| 未声明修订引入的新表面     | 新表面在后续轮次被偶然发现，形成 3 层缺口链  |
| reviewer 无严重度闸门      | 低级别、两行可修的问题也占用一整轮往返       |
| author 默认接受            | 92% 接受率，双方无摩擦，循环无自然阻尼       |
| 复述对方内容进行转发       | 同一内容产生两个副本，副本漂移               |

## 7. 待定

以下需要在编排层设计时确定，本契约不预设：

- **并发**：是否允许双方同时处理不同议题。当前布局（一议题一文件）在文件层支持，但 `MAILBOX.md` 是单点写入，需要串行化或改为可合并结构。
- **`decisions.md` 的规模上限**：36 个议题时约 500 行仍可读；若单次评审远超此规模，可能需要按主题分片。
- **议题级别的定义**：`阻塞 / 高 / 中 / 低` 在实验中由 reviewer 凭判断给出，无客观标准。若严重度闸门要机器执行，需要更可操作的定义。
- **跨评审复用**：事实表（`F<n>`）在同一代码库的多次评审间是否可继承。
